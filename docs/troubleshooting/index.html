Troubleshooting#

Chapter 22 of 23Source: docs/troubleshooting.md

Real problems, found in rehearsals and in the code, with what to do about them.

The console shows a ws://…:7457 error#

Every show made with createShow() tries to stream to the backstage monitor at ws://<the page's host>:7457. When no monitor is running, the browser logs the refused connection. This is expected and harmless: the page retries with a growing delay (about 5 s, rising to 30 s) instead of spamming. To make it go away, run the monitor:

bash
npm run monitor          # node packages/monitor/server.js

Pages served over https (openaudiovisual.com, an https tunnel) don't try at all: the browser blocks ws:// there, and a published site has no relay beside it. A show that runs a monitor behind TLS passes the address itself: createShow({ monitor: { url: 'wss://…' } }), or new MonitorFeed({ url: 'wss://…' }) in a hand-assembled show. A machine that should not look for a monitor at all (a performance PC with no backstage) says createShow({ monitor: false }): no feed is built and the page opens no socket, so nothing is logged.

Chrome asks about the local network, or about apps on this device#

Chrome's Local Network Access check puts a permission prompt in front of a public https page that tries to reach your own machine or network; a page served from your machine is not covered (Chrome blog). What it gates, by Chrome version (checked 2026-10-15):

  • Chrome 142: fetch requests (Chrome blog).
  • Chrome 145: two permissions, one for the local network and one for this device itself, called loopback (Chrome Platform Status).
  • Chrome 147: WebSocket and WebTransport connections as well (Chrome Platform Status).
  • Chrome 154: new WebSocket(url, { targetAddressSpace }) lets a page say which kind of address it expects (Chrome Platform Status).

When a show runs on openaudiovisual.com or another https site, three things of ours reach for your machine: the OSC bridge (OscOut posts to http://127.0.0.1:7456), the backstage monitor (ws://127.0.0.1:7457) and the Leap bridge. The first time, Chrome asks. If you chose Block, the connection fails, and the console shows net::ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS (seen on Chrome 154, Leap package notes).

What to do:

  • Press Allow. If you blocked it, open the page's site settings (the icon left of the address) and allow it again, then reload.
  • Or open the page from your own machine: node serve.js, then http://localhost:8080/…. That page is not a public site, so Chrome does not ask. This is the safest way to teach or rehearse the OAV → OSC → TouchDesigner path.
  • In an <iframe>, a cross-origin frame needs allow="loopback-network"; a same-origin frame inherits it; a sandboxed frame cannot get it (verified on Chrome 154, Leap package notes).
  • The device check has a button that tries the bridge and the monitor and says which one answered. It connects only when you press it.

The phone join card says "relay offline"#

On your own machine the phone relay lives inside serve.js (/relay). So the card says "relay offline" when the page was opened from a file, or from a server that is not node serve.js: run the show with node serve.js and open it from there.

On a static host (openaudiovisual.com, GitHub Pages) the show uses the public relay instead and the card reads relay ok · … · public relay with a QR code. If it says can't reach the relay (wss://remote.cheyuwu.com/relay) — retrying:

  • the network blocks WebSockets (some school and office Wi-Fi does): try a phone hotspot, or run node serve.js on a laptop on the same network as the phones;
  • the public relay is busy or down: it limits each address to 24 connections and 30 new connections a minute, which a whole classroom behind one router can hit. Run your own (node packages/relay/server.js) and open the show with ?relay=wss://your.host/relay;
  • ?relay=off is in the URL, which turns the remote off (the card is not drawn).

The phone opens the link in the QR code, which carries the room and the relay. If the phone says it is connected but nothing moves, check that both show the same #room and that the computer's page was not reloaded into a new room (the room is kept per browser, so another browser or a private window gets a different one).

No MIDI devices appear#

Run the device check first: it tells you whether this browser has Web MIDI at all.

  • Use Chrome or Edge. Safari has no Web MIDI (WebKit bug 107250, still open), and Firefox has it only after you install its site-permission add-on (Firefox 108). More in Which browser.
  • Allow MIDI when the browser asks. Since Chrome 124 it asks for any MIDI use (Chrome blog). The permission is per site: allowing it on localhost:8080 does not allow it on localhost:3000.
  • The device was plugged in after the page loaded: it should appear by itself. If it does not, reload.
  • Check the L1 · Input panel: a device with its box unticked is muted.
  • Another program may hold the port exclusively (some DAWs and drivers on Windows do). Close it.

A DAW on the IAC bus is not heard#

By default the Midi engine ignores every input whose name contains IAC (filterOut: 'IAC'). A show that sends MIDI out through the macOS IAC bus would otherwise hear its own output and loop. createShow() uses that default. To receive from a DAW over IAC, turn the built-in engine off and make your own:

js
import { Midi } from '@openav/midi';

const show = await createShow({ world, modules: { midi: false } });
const midi = new Midi({ signals: show.signals, filterOut: null });   // or a narrower regex
await midi.enable();

Your engine publishes into the same signals, so routes and worlds work unchanged. (The console's device list and MIDI meter only follow the engine createShow() made.) Do not send MIDI out to the same IAC bus you listen to.

A second guard needs no setting: a message that arrives on any input within 40 ms of an identical one the engine just sent is taken for the echo and dropped (new Midi({ echoWindow }), 0 turns it off, midi.echoDropped counts them).

The DAW went silent after a cable was pulled#

It should not any more. When the output port is unplugged Midi moves to the next best live port, prints one line in the MIDI log and one in the browser console (MIDI out: switched to "…" ("…" was unplugged)), and the L1 · Input panel's MIDI out → row follows. When the port you chose is plugged in again the output goes back to it. If the line says no output left, nothing is plugged in: messages are dropped until a port appears. Choose your port with midi.selectOutput(name) (or enable(name)) so it is the one that returns, and add new Midi({ prefer: ['IAC'] }) to say which port stands in first.

With two controllers, a route reacts to both#

With two or more MIDI inputs, each device publishes under its own name (midi/<slug>/cc/74) and under the shared legacy name (midi/cc/74). A route on midi/cc/74 hears every device; change its source to the per-device name. The slugs are shown in the L1 · Input panel.

QWERTY keys do not play#

Tick keyboard above the piano first. Capture is off by default so that typing never fights the console's hotkeys. Then A W S E D F T G Y H U J K O L P ; play, Z/X change octave.

While keyboard is ticked the letters belong to the piano, so the console's R (reset), T (prompter) and F (fullscreen) do nothing: T and F are piano keys, and an accidental R must not rewind a show you are playing. Space, the arrows and Esc still work, and Esc leaves capture.

Learn bound the wrong signal#

Learn binds the first signal that moves by 5% of its range, or the first pulse of any kind. The simulated performer and the drum machine send pulses all the time. Untick simulate performance, stop the drum machine, then click learn again. Remove the wrong route with ✕ in L2 · Mapping.

The timeline no longer moves a param#

A touched slider or a mapped signal overrides the param, and overrides are sticky: the score yields to the human. Clear it with ✕ next to the param (or show.params.clearOverride(key); clearAllOverrides() for all). A smoothed route keeps writing after its signal arrived, even when muted; remove the route to give the param back to the timeline. See Overrides and the timeline.

I changed a route in code and nothing changed#

The mapper saved yesterday's routes in localStorage, and a saved source → target pair wins over the declared one (new pairs are still added). Clear the profile, or pass profile: false while you develop:

js
localStorage.removeItem('openav.map.<world name>');

A route to sound/cutoff only moves between 0 and 1#

outMin/outMax default to the target's range when the route is added, and in createShow() declared routes are added before the sound engine registers its sound/* params. Give the range explicitly: { source: 'midi/cc/74', target: 'sound/cutoff', outMin: 100, outMax: 8000 }.

The camera or microphone does not start#

  • The page must be a secure context: http://localhost or https://. A LAN address over plain http:// (http://192.168.1.20:8080) is blocked.
  • The 🎤 mic, 🖐 hands and 🕺 body buttons must be clicked; nothing starts on its own. A button that reads ✗ retry failed: the reason is in the browser's devtools console.
  • On macOS, the browser itself needs camera and microphone access in System Settings → Privacy & Security.
  • Hands and body load MediaPipe and its model from jsDelivr and Google's storage the first time. Offline, they cannot start.

There is no sound#

Browsers start audio only after a click. Press 🔊 enable sound in the L4 · Output — sound panel. The Tone.js engine is loaded from jsDelivr at that moment, so the first time needs a network connection. The piano loads about 2 MB of samples the first time you pick it: the picker shows the progress, and the previous instrument keeps playing until the piano is ready. The drum machine's kit starts on the first hit after you tick drum machine.

A p5.js sketch with the one line misbehaves#

oav-p5 says what went wrong on the page: a card beside the 🎹, in the browser's language, with what happened, why and what to press (When something goes wrong). 🎹 → 🩺 puts the version, the microphone, MIDI, sound, the drums and the wiring on one card: screenshot it when you ask for help. The common ones:

  • knob1 is not defined: the line did not load (offline, or a typo in the URL). It goes first in the sketch, above setup().
  • Silence: browsers play audio only after the page has been clicked, and a key on a MIDI keyboard does not count. Click the canvas once; until then the 🔊 on the 🎹 button is yellow.
  • The drums are late on a Bluetooth speaker (0.15–0.25 s): ?oav_drumlatency=200 sets the delay by hand, in milliseconds.
  • The video is WebM: Firefox and older Chrome cannot write MP4, and Instagram does not take WebM. Record in Chrome 126 or later, Edge or Safari.
  • The microphone stays at 0 in a sketch embedded in another page: its <iframe> needs allow="microphone" (and allow="midi" for a hardware controller).

Strudel does not hear OAV Virtual MIDI#

OAV was loaded after Strudel's midin() ran, so midin('OAV Virtual MIDI') gets nothing and says nothing. Put await import('https://openaudiovisual.com/p5/oav-p5.js') in Strudel's settings → prebake (single quotes), save and reload: the prebake runs before your code. Until then 🩺 says "no program has asked OAV Virtual MIDI for MIDI". More in With Strudel.

The phone's tilt and knocks do nothing on an iPhone#

iOS only gives motion sensors to https:// pages, and only after a tap on 開始 (start). Over plain http:// on the LAN, touch, keys and the control surface still work. Reach serve.js through an HTTPS tunnel for sensors. If the permission was denied once, iOS keeps saying no until you change it in Settings → Safari → Motion & Orientation Access, then reload.

After a deploy, the site still runs old code#

GitHub Pages lets browsers cache JavaScript for hours while HTML expires in minutes, so a visitor can get new HTML with old modules. Before deploying, run node tools/stamp-version.mjs: it appends ?v=<commit> to module URLs in the examples, packages and homepage. Locally this never happens: serve.js sends Cache-Control: no-store.

The show slows down when the window is in the background#

Browsers pause requestAnimationFrame in hidden tabs. The Loop then keeps running from a Web Worker at about 15 frames per second, so the timeline, mapped signals and the backstage feed continue, but rendering is slower. Keep the projection window visible, on its own screen, in fullscreen (F).

An example from a CDN works online but not offline#

p5 (examples 05, 06), Tone.js (sound), MediaPipe (hands, body) and the WebToe app (example 04) come from the network. For an offline venue, download them and point the script tags, the import map or the module options (toneEngine({ cdn }), webtoeWorld({ app })) at local copies.

The port is already in use#

node serve.js 8081 serves on another port, and the OSC bridge takes one too: node packages/osc/bridges/osc-bridge.js 7470 (then new OscOut('http://127.0.0.1:7470')). The backstage monitor is the exception: a createShow() page streams to port 7457 on its own host unless you say otherwise, so free that port, or point the show elsewhere with createShow({ monitor: { url: 'ws://host:7460' } }) (in a hand-assembled show: new MonitorFeed({ url: 'ws://host:7460' })) and start the relay with node packages/monitor/server.js 7460.

The output window does not open, or stays black#

A browser opens a window only from a click, so outputs.open() and openOutput() work in a button's handler and throw "the browser blocked the output window" anywhere else; a popup blocker can also stop one click (allow popups for this site). A mirror shows the stage's <canvas>: a world drawn with DOM or SVG has none, and the window says so (use { mode: 'page' }). After the show page reloads, a mirror keeps its last picture: open the output again from the page. On one screen, an output in fullscreen over the show page hides that page, and the mirror slows to the hidden-tab rate (above): put the output on another screen, or leave it a window. See Projection and video out.

A screen on the table is not placed by the photo#

The camera page's list says why for each screen. too-few-markers: fewer than four of its markers were read, so take the photo again from closer or straighter, with less of it covered, the brightness up and no lamp reflected in it. A screen missing from the list has not said hello: it is in another room, or not on the relay (a static host has none: run node serve.js), or two tabs of one browser share an id (add &id=a). A screen placed once and drawing on its own again changed size (a rotation, the browser bars): fullscreen it, then take a new photo. On an iPhone, add the page to the home screen for fullscreen. The first photo waits for OpenCV.js (about 3 MB from jsDelivr); with no internet the camera page cannot detect. See Several screens, one canvas.
